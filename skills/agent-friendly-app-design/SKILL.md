# AIが使えるアプリ設計（Agent-Friendly App Design）

## 概要（発動条件）

- 自作アプリを AI エージェントが GUI を叩かずに操作・検証できるようにしたいときに使う。発動例は「CLI対応にして」「AIが使いやすくして」「エージェントから操作できるように」「自動で検証できるように」「API／コマンドを用意して」「MCP対応にして」「SDKを用意して」である。

- 対象は Android、Flutter、Web、Space、デスクトップ、スクリプトなどプラットフォームを問わない。対象は利用者自身が作るアプリであり、外部サービスへの接続ではない。

- このスキルが扱うのは「機械がどう操作するか」の設計である。何を見せるかは meaningful_app_design の領分、外部サービスの接続は custom_connector_setup の領分、画面の交付前検証の実施手順そのものは、利用側の検証標準（スクリーンショットテストと単体テストによる実機なし検証）の領分である。

- 作業の範囲は依頼で決める。段階依頼（「監査だけ」「読み取りだけ」）ではその範囲で止まる。通し依頼では監査、設計、実装、検証まで進める。

## 核：GUI と同じ芯を、機械にも開く

- アプリの業務ロジックを UI から分離し、GUI と CLI／API が同じ芯（サービス層）を共有する形を正とする。CLI 用に別の実装を作らない。

- 人間が画面でできる主要操作は、原則として機械からも同じ結果で実行できるようにする。できない操作は隠さず、理由付きで人間専用と宣言する。

- AI が安全に使える条件は次の 4 点が揃うことである。読み取れる、操作できる、結果を確認できる、失敗しても壊れない。

- 見た目の良し悪しや人間の使いやすさを犠牲にして機械対応を優先しない。機械対応は裏側の契約であり、画面の情報量を増やす理由にしない。

## 到達レベル：L0 から L4

- 作業の最初に対象アプリの現在レベルを判定し、目標レベルを 1 つ決める。全アプリを最初から L4 にしない。

- L0 は GUI のみである。状態も結果も画面でしか分からない。

- L1 は読み取り可能である。状態、一覧、履歴、設定を JSON で取得できる。

- L2 は操作可能である。主要操作を CLI／API で実行でき、作成、変更、削除、有効化、無効化が GUI と同じ芯を通る。

- L3 は検証可能である。ドライラン、検証コマンド、決定的なテストデータ、スクリーンショット取得で AI が結果を自分で確認できる。

- L4 は自律運用に耐える。冪等性、監査ログ、破壊的操作の安全弁、バージョン付きスキーマが揃い、AI が繰り返し実行しても壊れない。AI が日常的に自律運用するアプリでは、MCP 対応を L4 の条件の 1 つとする。

- 既定の目標は L2 とし、日常的に AI が触るアプリだけ L3 以上を目指す。読み取りだけ必要なアプリは L1 で止めてよい。

- MCP と SDK はレベルとは別の層として扱う。MCP は CLI の上に被せる AI 専用の玄関であり、SDK は他の開発者と他のアプリ向けの部品である。土台の CLI を飛ばして上層だけを作らない。

## 操作カタログ：最初に作る正本

- 実装の前に、アプリの全操作を操作カタログとして 1 枚に棚卸しする。保存先はプロジェクトの慣例に従い、無ければ `docs/AGENT_OPERATIONS.md` とする。

- 1 操作ごとに記録する。操作名、対象、人間の手順、機械の経路、入力、出力、副作用、破壊的かどうか、人間専用かどうかとその理由。

- カタログに無い操作を CLI へ場当たりで足さない。先にカタログへ登録し、狙いを添えてから実装する。

- 棚卸しの粒度は「利用者が画面で名前を言える操作」までとする。内部の小処理はカタログではなくコードが持つ。

## CLI 契約

- 主要機能はサブコマンドで構成する。基本形は `list`、`get`、`create`、`update`、`delete`、`run`、`status`、`history`、`export`、`import`、`doctor`、`verify` とし、アプリに無い操作は無理に作らない。

- すべてのコマンドに `--help` を付け、使い方、必須引数、例を 1 画面で返す。ヘルプだけで典型フローが分かる状態を合格とする。

- 全コマンド共通のフラグを用意する。`--json`、`--dry-run`、`--yes`、`--idempotency-key <key>`、`--timeout <sec>` である。対応しないフラグは黙って無視せず、未対応と明示する。

- 終了コードを統一する。0 は成功、1 は利用者の入力誤り、2 はアプリ側の失敗、3 は権限不足、4 は対象が無い、とする。終了コードだけで成否が分かるようにする。

- 破壊的操作は既定で確認を求め、自動実行では `--yes` を必須とする。削除は可能な限り取り消し可能にし、即時完全削除は最後の手段とする。

- 冪等性を守る。同じ `--idempotency-key` の再実行は二重に作らず、最初の結果を返す。ネットワーク再試行で重複が起きる操作は必ず冪等キーに対応する。

- 長い処理は同期で黙らせない。進捗かジョブ ID を返し、`status` で続きを確認できるようにする。

- プラットフォーム別の実現方法は [プラットフォーム別パターン](references/platform-patterns.md) を使う。Android の adb 経由、Flutter のテスト経路、Web の API と CLI ラッパー、Space のアクション経路をそこに正本化する。

## 機械可読な入出力

- 機械向け出力は JSON を正とし、人間向け整形は `--human` など別経路にする。同じコマンドで両形式を混ぜない。

- 成功の包みを統一する。`{"ok": true, "data": ..., "meta": {"schema_version": 1, "request_id": "..."}}` の形を基本とする。

- 失敗の包みを統一する。`{"ok": false, "error": {"code": "not_found", "message": "...", "retryable": false, "details": {...}}}` の形を基本とし、エラーコードは文字列の定数で安定させる。

- ID は安定させる。再利用しない UUID か ULID を正とし、表示名や並び順を ID の代わりにしない。読み込みで ID を振り直す場合は旧 ID と新 ID の対応を出力する。

- 日時は ISO 8601 とタイムゾーン付きで出し、金額、長さなどの単位はフィールド名か単位フィールドで明示する。相対表現（「さっき」「3件目」）を機械向け出力に使わない。

- スキーマにバージョンを持たせる。互換を壊す変更はバージョンを上げ、移行方法を AI 向けドキュメントに書く。

- 秘密情報を出力に含めない。API キー、トークン、パスワードは存在の有無だけを返し、値そのものは返さない。

## 状態の読み取り

- 現在の状態を読み取り専用で取得できる経路を最初に作る。書き込みより先に読み取りを揃えるのが後付けの鉄則である。

- 最低限そろえる読み取りは次の 4 つである。アプリ情報と版数（`status`）、主要データの一覧（`list --json`）、1 件の詳細（`get <id> --json`）、直近の実行と失敗の履歴（`history --json`）。

- 権限と前提条件の状態も読み取れるようにする。不足している権限、未設定のキー、接続状態を `doctor` が一覧で返し、画面を開かなくても詰まりの理由が分かるようにする。

- 読み取りコマンドは副作用を持たない。読むだけで状態が変わる経路は作らない。

## 検証可能性

- 書き込み系コマンドには `--dry-run` を付け、実際に変えずに「何がどう変わるか」を JSON で返す。AI は本実行の前に必ずドライランで確認できる。

- `verify` コマンドを用意し、データ整合性、前提条件、代表操作の自己点検結果を合格か不合格かで返す。不合格のときは理由と直し方をエラー形式で返す。

- テスト用に初期データを投入する `seed` と、テスト状態へ戻す `reset --test-data` を用意する。本番データに対しては実行できないようガードする。

- 決定的モードを用意する。時刻、乱数シード、ネットワーク応答を固定でき、同じ入力で同じ結果になる状態で検証できるようにする。

- 画面の検証は既存の標準に従う。Android はスクリーンショットテストと Robolectric、Flutter は widget テストと golden テスト、Web は安定したセレクタ（`data-testid`）とスクリーンショット取得経路を用意する。

- 実行結果はトーストや一時表示だけで終わらせない。履歴として残し、後から `history` で成功と失敗理由を確認できるようにする。

## MCP 層：CLI を AI 専用の玄関として公開する

- MCP は CLI と JSON スキーマが揃った後に被せる層とする。先に MCP サーバーだけを作らない。土台が無い MCP は呼び出しのたびに画面操作へ逆戻りする。

- 対応の目安は、AI が日常的に触るアプリだけとする。全アプリ一律に MCP 化しない。サーバーの運用、版数管理、認証という維持費が増えるためである。

- 対応表を固定する。書き込みと実行のコマンドは MCP のツール（tools）にする。読み取り専用の状態、一覧、履歴は MCP のリソース（resources）にする。典型フローの手順書は必要に応じてプロンプト（prompts）にするが、無くてもよい。

- スキーマは単一の正本から生成する。入出力スキーマの正本は CLI 側の定義とし、MCP のツール定義はそこから生成か機械変換する。CLI と MCP で別々に手書きして二重管理にしない。

- ツール名はコマンド名と一致させる。`list` コマンドは `list` ツールとし、名前の翻訳や別名を作らない。説明文には何をするか、副作用、破壊的かどうかを書き、AI が説明だけで安全に選べるようにする。

- 安全性は CLI と同じにする。破壊的ツールはドライラン相当の引数を持ち、既定では実行しない。冪等キー、終了コードに相当する成否とエラーコードもツール結果に同じ形式で返す。

- 認証と公開範囲を明示する。MCP サーバーは原則ローカルか認証付きで公開し、書き込み系ツールは読み取り系と分けて有効化できるようにする。秘密情報はツール結果に含めない。

- 許可するツールを列挙して固定する。サーバーが後から追加したツールは、内容を確認して許可リストへ加えるまで使えない扱いとする。これは外部 MCP サーバーを利用するときの作法（custom_connector_setup の MCP-backed CLIs）と同じである。

- プラットフォーム別の置き方は [プラットフォーム別パターン](references/platform-patterns.md) の MCP の節を使う。特に Android は端末内常駐ではなく、PC 側の薄いサーバーが adb 経由で CLI や Intent を叩く橋渡し型を既定とする。

- MCP 化しても CLI を残す。MCP は発見と呼び出しを楽にする層であり、テスト、障害対応、人間の確認では CLI がそのまま使えることが保険になる。

## SDK 層：作らないのが既定

- SDK は AI のためではなく、他の開発者と他のアプリが部品として組み込むためのものと位置づける。個人開発のアプリの主な利用者が AI と作者本人である限り、SDK の優先度は低い。

- 作る条件は次のいずれかとする。他の自作アプリから同じ芯を再利用したい需要が実際に出たとき、外部の開発者へ公開する方針が決まったとき、型付きの組み込みが CLI 呼び出しより明確に安全になる場面が出たときである。

- 作る場合は言語を 1 つに絞る。そのアプリの主言語（Kotlin、Dart、TypeScript のいずれか）だけを正とし、複数言語へ同時展開しない。

- SDK は芯のサービス層への薄い型付きラッパーとし、業務ロジックを SDK 側へ複製しない。版数はアプリ本体とスキーマ版数に連動させる。

- 需要が出るまでは、代わりに JSON スキーマと AI 向けガイドを整えておく。それだけで AI とスクリプトからの利用は足りる。

## AI 向けドキュメントの同梱

- アプリ内に AI 向けドキュメントを同梱する。正本は `docs/AGENT_GUIDE.md` とし、テンプレートは [AI 向けガイドのテンプレート](templates/agent-guide-template.md) を使う。

- ガイドには最低限次を含める。アプリの目的 1 行、到達レベル、コマンド一覧と典型フロー 3 本、入出力スキーマとバージョン、エラーコード表、人間専用操作の一覧と理由、ドライランと検証の手順、やってはいけない操作。

- 機械可読な目録も同梱する。`docs/agent-manifest.json` にアプリ名、版数、スキーマ版数、対応コマンド、到達レベル、MCP の有無と接続先、SDK の有無を書き、AI が最初にこれだけ読めば全体像が分かるようにする。様式は [チェックリスト](references/checklist.md) の末尾を使う。

- ガイドと実装がずれたら実装バグとして扱う。コマンドを変えた作業は、ガイドと目録の更新まで含めて初めて完了とする。

## GUI しかない機能の扱い

- GUI しかない操作は 3 つに仕分ける。A は経路を作れば機械化できるもの、B は画面まで案内できるもの、C は人間専用のものである。

- A は意図、API、ファイル受け渡しなどで代替経路を作り、操作カタログへ登録する。

- B はディープリンクや事前入力で対象画面を正確に開くところまでを機械が担い、最後の 1 操作だけ人間が行う。開く画面と渡す値をガイドに書く。

- C は人間専用と明示する。対象は生体認証、OS の権限ダイアログ、支払い確定、CAPTCHA、身体感覚の判定（見え方、触り心地、音の質感）である。理由を 1 行で書き、代替の自動化を偽装しない。

- C を無理に自動化しない。人間専用の一覧が正直に揃っていること自体を、このスキルの合格条件とする。

## 進め方：新規アプリ

- コンセプトが固まったら、画面設計の前に操作カタログの初版を作る。

- 芯のサービス層を先に決め、GUI と CLI が共有する境界を設計に書き込む。UI フレームワークの中に業務ロジックを埋めない。

- 最初から `status`、`list --json`、`--dry-run`、`verify` の 4 点を最小セットとして組み込む。書き込みコマンドはその後に足す。

- AI 向けガイドと目録の雛形を初版リリース前に置き、到達レベルを正直に書く。

## 進め方：既存アプリへの後付け

- まず現状を監査する。データの保存場所と形式、外部から触れる経路の有無、ID の安定性、履歴の有無、テスト基盤の有無を記録する。様式は [チェックリスト](references/checklist.md) を使う。

- 後付けは読み取りから始める。順番は `status`、次に `list` と `get`、次に `history` と `doctor`、最後に書き込み系である。読み取りが揃う前に書き込みを自動化しない。

- 既存の入出力機能を土台にする。JSON の書き出しと読み込み、共有機能、バックアップ機能が既にある場合は、そのスキーマを正式化するところから始める。

- 保存形式が画面都合で不安定な場合は、芯の層を 1 枚挟んでから機械経路を開く。保存形式へ直接依存する CLI を量産しない。

- 後付けの各段階で到達レベルを更新し、ガイドと目録へ反映する。1 回で L4 を目指さず、段階ごとに動く状態で渡す。

- MCP 対応は後付けの最後の段階とする。L2 の操作と L3 の検証が動いてから、コマンドをツールへ変換する。SDK は後付けの対象に含めず、需要が出た時点で別作業として扱う。

- 具体的な当てはめ例は [きっかけへの当てはめ](references/kikkake-worked-example.md) を参照する。監査、優先順位、段階計画の書き方の見本である。

## 他スキルとの連携

- 何を作るかと機能の要否は concept-driven-ux スキルの領分とする。このスキルでは機能を発明しない。

- 見た目と情報設計は meaningful_app_design と minimal_information_design の領分とする。機械対応を理由に画面へ説明やボタンを足さない。

- 外部サービスを操作する経路が必要になったら custom_connector_setup スキルでコネクタとして切り出す。自作アプリ内部の機械経路はこのスキル、外部サービスはコネクタ、と分ける。

- 画面検証の実施手順は利用側の検証標準に従い、このスキルでは検証できる状態を作ることまでを担う。

## 最後に簡潔に報告する

- 次を日本語で伝える。対象アプリと現在レベルと目標レベル、操作カタログの保存先、実装したコマンドと未実装のコマンド、入出力スキーマの版数、MCP 対応の有無とツール一覧、SDK の要否の判断、人間専用と宣言した操作と理由、ドライランと検証の実行結果、AI 向けガイドと目録の保存先、未確認の範囲である。

- 設計、実装、動作確認の状況を分けて書く。Git 管理下ではコミット ID または未コミットの理由も示す。

## Available connectors

## Alternatives for better results

- 外部サービスを AI から操作したい場合は、このスキルではなく custom_connector_setup スキルでコネクタを作る。

- 単発の自動操作だけが目的でアプリ自体を変えたくない場合は、ブラウザ操作や adb 操作で済ませ、恒常的な機械経路を作らない。
