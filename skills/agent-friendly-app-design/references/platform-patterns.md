# プラットフォーム別パターン

プラットフォームごとに「機械経路の作り方」は違うが、契約（JSON、終了コード、安定 ID、ドライラン）は共通にする。

## 共通の原則

- どのプラットフォームでも芯は 1 つにする。GUI 用と機械用で別実装を作らない。
- 機械経路は開発ビルドだけに閉じない。本番でも安全な読み取り経路は残し、危険な経路だけ開発用に閉じる。
- 開発用経路を本番へ残す場合は、権限と公開範囲を明示し、書き込み系は認証かデバッグ署名で守る。

## Android（Kotlin / Compose / Views）

- 読み取りと操作の第一候補は次の順で検討する。
  1. アプリ内のデバッグ／運用用 Activity や Service を Intent で叩く経路（`adb shell am start`、`adb shell am broadcast`）
  2. `adb shell cmd` へ登録できる自前のコマンド経路
  3. ContentProvider の読み取り専用公開（権限で守る）
  4. ファイル受け渡し（JSON の書き出しと読み込みを正式スキーマ化する）

- データが SharedPreferences や端末内 DB に閉じている場合は、まず書き出しスキーマを正式化し、次に Intent 経路を足す。`run-as` 前提の直接読みはデバッグビルド限定と明記する。

- テスト実行や状態変更の結果は Toast だけで返さない。結果 JSON をファイルか履歴 DB へ残し、`history` 相当で回収できるようにする。

- OS の権限ダイアログ、生体認証、正確なアラーム許可などの付与操作は人間専用（C）に分類する。不足の検出は `doctor` 相当で機械化する。

- 画面検証は Robolectric と Roborazzi か Paparazzi のスクリーンショットテストを使い、主要画面と遷移を JVM で確認する（実機なし検証の標準）。

## Flutter

- 芯は Dart のサービス層に置き、Widget は表示に徹する。機械経路は Dart 側の同じサービスを叩く。
- 検証は widget テストと golden テストを正とし、`integration_test` で実フロー（起動、一覧、作成、実行）を通す。
- 開発用には `--dart-define` で決定的モード（固定時刻、固定シード、モック応答）を切り替えられるようにする。
- ネイティブ側の機能（通知、権限、センサー）はプラットフォームチャネル越しの結果を構造化して返し、成功か失敗かを文字列表示で終わらせない。

## Web / Space

- 機械経路の正は HTTP API（JSON）か、Space の宣言済みアクションとする。画面の DOM をスクレイピングさせる設計にしない。
- API が無い小規模な Web では、同じ API を叩く薄い CLI ラッパースクリプトを同梱し、AI はブラウザではなくラッパーを使う。
- 画面検証用に安定した `data-testid` を主要要素へ付け、文言やクラス名の変更で検証が壊れないようにする。
- 認証が必要な操作はトークンの有無だけを `status` で返し、値自体は返さない。

## デスクトップ / スクリプト / CLI ネイティブ

- 最初からサブコマンド構成にし、`--help` と `--json` と終了コードの統一を初版から守る。
- 設定と状態はファイルの場所を `status` で開示し、環境変数での暗黙の切り替えに依存しない。
- ログは標準エラーへ、機械可読な結果は標準出力へ分ける。混ぜると JSON が壊れる。

## MCP サーバーの置き方（プラットフォーム別）

- Web / Space はサーバー型が素直である。アプリの API と同じホストに MCP サーバーを置き、ツールは内部で既存 API を叩く。stdio 型はローカル開発用に限る。

- Android / Flutter のモバイルアプリは橋渡し型を既定とする。端末内で MCP サーバーを常駐させず、PC 側に薄い MCP サーバーを置き、ツール呼び出しを adb 経由の CLI や Intent 実行へ変換する。端末がつながっていないときは、ツールを失敗として返し、理由をエラーコードで明示する。

- デスクトップとスクリプトは stdio 型が素直である。CLI 本体を子プロセスとして起動する MCP ラッパーを同梱し、コマンドとツールを 1 対 1 に対応させる。

- どの型でも、ツール定義は CLI のスキーマ定義から生成する。生成の仕組みが無い小規模アプリでは、対応表を 1 枚（コマンド名、ツール名、種別、副作用）で管理し、ズレを検証コマンドで検出する。

- MCP サーバーの接続情報（起動方法、接続先、認証の要否、ツール一覧）は AI 向けガイドと `agent-manifest.json` の両方へ書く。

## どれにも当てはまらない場合

- 機械経路が作れないプラットフォーム機能は、無理に作らず B（画面まで案内）か C（人間専用）に分類し、理由をガイドへ書く。
- 分類に迷う操作は、まず読み取りだけでも機械化できないか検討し、それも無理な場合だけ C にする。
