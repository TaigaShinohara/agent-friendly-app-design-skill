# 当てはめ例：きっかけ（Kikkake）v2.2.5

このスキルを既存アプリへ当てた監査と段階計画の見本である。公開リポジトリ TaigaShinohara/kikkake（SPEC v2.2.5、Store.kt、Engine.kt、docs/VERIFICATION.md）を実コードで確認して作成した。実装はしていない。監査結果のみである。

## 対象の事実

- Android アプリ。パッケージは `com.taigashinohara.kikkake` である。
- 自動化（Macro）は、きっかけ 16 種、やること 38 種、条件から構成される。`Macro.id` は Long 型である。
- 保存は SharedPreferences の `macros` に JSON 文字列で保持される。保存と読み込みは `MacroStore` に集約され、UI から分離された芯が既にある。
- 書き出しと読み込みの JSON 関数（`exportJson` / `importJson`）が既にある。ただし読み込み時は `System.currentTimeMillis()` を基に ID を振り直し、対応表は返さない。
- 実行履歴は `StateStore.runLog` に文字列で保持され、ホームに直近 5 件、保持は 20 件である。構造化された履歴ではない。
- テスト実行の結果は主に Toast とスナックバーで返る。後から機械が回収できる結果オブジェクトは無い。
- 開発側の検証基盤は強い。`run-tests.sh` が正本で Robolectric と Roborazzi の全 26 件が合格し、ゴールデン 6 枚を目視確認する運用が docs/VERIFICATION.md にある。
- 外部から叩ける CLI、API、Intent 経路は無い。Gemini API キーは `StateStore.aiApiKey` に端末内保存される。

## 現在レベルの判定：L0（開発検証だけ L3 相当）

- 利用者データの読み取り、操作、実行結果の確認はすべて GUI 経由のみのため、アプリとしては L0 である。
- 開発時の画面検証だけはスクリーンショットテストで AI が確認できるため、その一点は L3 相当である。アプリの機械対応と開発検証は分けて判定する見本とする。

## 操作カタログ（抜粋）

| 操作 | 人間の手順 | 機械化の仕分け | 備考 |
|---|---|---|---|
| 自動化の一覧を見る | ホームを開く | A：`list --json` | MacroStore.load が土台になる |
| 自動化を作る | ウィザード 3 ステップ | A：`create --file macro.json` | 既存の importJson が土台になる |
| オンとオフを切り替える | タイルのスイッチ | A：`enable <id>` / `disable <id>` | enabled フラグの変更のみ |
| テスト実行する | タイルのテストボタン | A：`run <id> --dry-run` と `run <id>` | 結果を構造化して履歴へ残すことが条件 |
| 実行履歴を見る | ホームの下部 | A：`history --json` | runLog の構造化が先 |
| 権限の不足を見る | ホームの権限チェック | A：`doctor --json` | 画面の権限チェックと同じ判定を返す |
| 権限を付与する | OS の設定画面 | C：人間専用 | OS ダイアログ必須。検出だけ機械化する |
| 声で知らせるの聞こえ方 | 実機で聞く | C：人間専用 | 身体感覚の判定。発火の成否だけ機械化する |
| AI キーを入れる | 設定ダイアログ | B：画面まで案内 | 値自体は機械へ渡さない。有無だけ `status` で返す |

## 優先順位と段階計画

### 第 1 段階：L1 読み取り（最初にやる）

- 書き出し JSON を正式スキーマ v1 として固定する。フィールド名、必須項目、版数を docs に書く。
- ID の扱いを直す。読み込みで振り直す場合は旧 ID と新 ID の対応表を結果に含める。将来は UUID 化を検討するが、この段階では Long のまま対応表で吸収する。
- 実行履歴を構造化する。1 件ごとに日時、自動化 ID、成否、失敗理由コードを持つ JSON 配列へ移行し、旧 runLog 文字列からの移行を付ける。
- デバッグビルド限定で Intent 経路を 1 本開け、`status`、`list`、`get`、`history`、`doctor` の読み取り 5 点を返す。結果は JSON ファイル経由で回収できる形にする。

### 第 2 段階：L2 操作

- `create`、`update`、`enable`、`disable`、`delete --dry-run / --yes` を同じ Intent 経路へ足し、処理は MacroStore と Engine の既存の芯を通す。
- テスト実行の結果を構造化する。動いた、一部だけ動いた、許可不足、を結果コードで返し、履歴へ残す。Toast は人間向けの補助に降格させる。
- 冪等キーを create に付ける。同じ JSON の再投入で二重に作らない。

### 第 3 段階：L3 検証

- `verify` でデータ整合性（不正な trigger や action の混入）と権限状態を自己点検する。
- テスト用シードとして、テンプレ 8 件のうち代表 2 件を決定的データとして投入できるようにする。
- 既存の run-tests.sh とスクリーンショットテストはそのまま開発検証の正本として維持し、AGENT_GUIDE から参照する。

### 第 4 段階：MCP 橋渡し（任意、L4 を目指す場合だけ）

- 端末内に MCP サーバーは置かない。PC 側に薄い MCP サーバーを置き、ツール呼び出しを adb 経由の Intent 実行へ変換する橋渡し型にする。
- 対応付けは、読み取り 5 点（status、list、get、history、doctor）をリソースと読み取りツールへ、書き込み系（create、enable、disable、run）をツールへ、そのまま 1 対 1 で行う。ツール定義は CLI のスキーマから生成する。
- きっかけは日常的に AI が触るアプリとは言い切れないため、この段階は急がない。先に L2 と L3 を安定させる方が先である。
- SDK は作らない。他アプリから Macro の芯を再利用する需要が出ていないため、既定どおり見送る。

### やらないこと

- 本番ビルドへ書き込み経路を無防備に開けない。書き込みはデバッグ署名か明示的な有効化でのみ開ける。
- AI キーの値を読み取り結果に含めない。有無だけを返す。
- GUI のウィザードを機械用に作り直さない。芯は共有し、画面は人間のままにする。

## この当てはめで分かったこと（スキルの検証結果）

- 芯（MacroStore / Engine）と保存形式（JSON）が既にあるアプリでは、第 1 段階は新規開発ではなく正式化の作業が中心になる。スキルの「既存の入出力を土台にする」手順がそのまま効いた。
- 弱点は ID の振り直しと履歴の非構造化と結果の Toast 依存の 3 点に集約された。監査チェックリストの「ID の安定性」「履歴」「結果の回収」の項目で漏れなく拾えた。
- 人間専用（C）の切り分けも自然にできた。権限付与と音の質感は無理に自動化せず、検出と発火成否だけを機械化する線が引けた。
